# Operations: migrations, RLS and backups

This document exists because the three things below get done **when something
is going wrong**, and that is not the moment to read TypeScript.

---

## First, and only once per database

> **If the database already exists, run `--baseline` BEFORE anything else.**

```bash
cd apps/api && bun run db:migrate:baseline
```

**Why.** For a long time there was no migration runner: the migrations in
`src/db/migrations/` were applied by hand with `psql`, and `db:migrate` was
`drizzle-kit`, which only knew about two of them. A database set up that way
**already has the schema**, but its migration history is empty.

`--baseline` marks everything present as applied **without running it**.
Without that step, the runner would try to reapply every migration on top of
real data.

It is a one-time command. On a new, empty database **do not use it**: there you
want the migrations to really run.

---

## Migrations

```bash
bun run db:migrate            # apply pending ones + RLS policies
bun run db:migrate:status     # what is applied and what is missing
bun run db:migrate:dry        # what would run, touching nothing
bun run db:migrate:baseline   # mark as applied without running (existing database)
```

It applies, in this order, which is not arbitrary:

1. `apps/api/drizzle/*.sql`: the base schema generated by drizzle-kit
2. `apps/api/src/db/migrations/*.sql`: the hand-written ones, which **extend** that base
3. The RLS files (`agent-functions.sql`, `rls-policies.sql`,
   `rls-owned-tables.sql` and `rls-system-only.sql`), all idempotent

Each file runs in **one transaction**: if a statement fails, the whole
migration is rolled back and the history does not record it. There are no
half-applied migrations.

The history lives in the `kitsuden_migrations` table, with the checksum of each
file.

### "These migrations changed AFTER being applied"

The runner refuses to go on. **It is right to refuse**: an applied migration is
history, and editing it does not reapply it. The database and the repository are
saying different things.

What to do is **add a new migration** that corrects it. `--allow-drift` exists
to force it, and should only be used when you know exactly why.

### "Postgres extensions the chain needs are missing"

The chain needs `vector` (pgvector) and `pg_trgm`. The runner checks this
**before** applying anything, because `CREATE EXTENSION IF NOT EXISTS` does not
protect you: it only stays quiet when the extension is already created, not when
it is unavailable.

In Docker, use an image that ships them:

```yaml
image: pgvector/pgvector:pg16
```

**In lite mode (PGlite) `vector` is not available.** That is a ceiling of lite
mode, not a configuration error: brain and semantic search cannot be migrated
there. Downgrading PGlite to 0.3.x, where it does exist, was tried and produces
about 100 type errors in the query layer, so it was dropped.

### "The connection uses X, which is a SUPERUSER"

A warning, not an error. **Postgres ignores RLS for superusers**, `FORCE` and
all: the policies become decorative and isolation between tenants is not
enforced. In production, connect with an ordinary role.

## Backups

```bash
bun run db:backup          # create (and verify)
bun run db:backup:list     # list
bun run db:restore <file>  # restore (asks for confirmation)
```

Variables: `BACKUP_DIR` (default `./backups`) and `BACKUP_KEEP` (default 7).

**Every dump is verified when it is written**, by reading its index with
`pg_restore --list`. If it cannot be read, it is deleted and the command fails.
A backup that has never been read is not a backup: it is a file, and the day you
find out it was corrupt is, by definition, the worst possible day.

Format `-Fc` (custom): compressed, and it allows restoring single tables. A
plain `.sql` can only be restored whole.

### Restoring

```bash
bun run db:restore kitsuden-2026-08-15T10-30-00.dump
```

It shows what it is about to overwrite and **refuses to go on**. To really
confirm:

```bash
bun run scripts/backup.ts --restore <file> --yes-i-am-sure
```

After restoring, **run the migrations**: the backup is from the moment it was
taken and may lack whatever was applied since.

```bash
bun run db:migrate
```

### Requirements

`pg_dump` and `pg_restore` must be installed, and their version must be **equal
to or newer than** the server's. If it is older, `pg_dump` refuses to dump. It is
the most common failure when taking backups from another machine.

In the API container:

```bash
apt-get install -y postgresql-client
```

**Lite mode cannot be backed up with `pg_dump`.** PGlite stores to local disk:
copy it with the file system.

## What happens on every deployment

`docker/start-with-check.sh`, step 4, runs `apps/api/scripts/migrate.ts`. That applies
the pending migrations and the RLS policies.

**There is no `||`**: if it fails, the container does not start. That is what we
want. An earlier version of that step swallowed errors and let the API start
with a half-built schema.

## What CI checks

On every push, against a real Postgres:

1. It builds the schema **from scratch**, applying the full chain
2. It runs a **second pass** and fails if it applies anything: a migration that
   is not idempotent breaks any deployment that gets retried
3. It runs the tests

### Guards: tests that do not test code

The suite contains several tests that check no behaviour but **repository
invariants**. If one goes red you have not broken a function: you have crossed a
line somebody drew on purpose. Each one carries its reason in its header and in
the failure message; here is the map.

| Guard                                                      | What it prevents                                                                                                                            | How to get out of red                                                                                                                       |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `tests/unit/any-ratchet.test.ts`                           | The number of unjustified `any` growing                                                                                                     | Type what you added, or add `eslint-disable-next-line @typescript-eslint/no-explicit-any -- <reason>`. The ceiling only goes down, never up |
| `tests/unit/ts-suppression-ratchet.test.ts`                | New `@ts-ignore`/`@ts-expect-error`, and any without an explanation                                                                         | Fix the type, or explain the suppression on the same line                                                                                   |
| `tests/unit/kon-typecheck-coverage.test.ts`                | Kons that declare no `typecheck` script, which `pnpm -r typecheck` would silently skip                                                      | Add `"typecheck": "tsc --noEmit"` and its `tsconfig.json`                                                                                   |
| `tests/unit/kon-loadable.test.ts`                          | Kons the loader would treat as failed at startup ("no router or init found")                                                                | Export `const kon = defineKon({ createRouter })`, a Hono router or an `init*` function                                                      |
| `tests/unit/uncast-enum.test.ts`                           | `eq(column, value as any)`: if the column is a Postgres enum, a value outside it fails the whole query (500) instead of returning zero rows | Use `eqEnum(column, value)` from `@kitsuden/engine`                                                                                         |
| `tests/unit/mcp-validated-args.test.ts`                    | MCP tools without a schema: an LLM writes the arguments and they reach `.insert()`                                                          | Add the tool's entry to `ARGS_SCHEMAS` in `mcp-tools.ts`                                                                                    |
| `tests/unit/guard-drizzle-where.test.ts`                   | (at RUN time) a second `.where()` call on the same builder, wherever it comes from, helper functions included                               | Pass the CONDITIONS between functions, not the builder                                                                                      |
| `tests/unit/drizzle-chained-where.test.ts`                 | Filters accumulated with a repeated `q = q.where(...)`: in Drizzle the second one REPLACES the first and the query returns too much         | Accumulate in an array and call `.where(and(...conditions))` once                                                                           |
| `tests/unit/engine-facade-cycles.test.ts`                  | A file that deep-imports the engine also importing the facade and reopening the cycle                                                       | Deep-import the missing piece too (for example `packages/engine/src/errors.ts`)                                                             |
| `apps/api/src/tests-unit/rls-coverage.test.ts`             | New tables without an RLS policy                                                                                                            | Classify the table and add its policy to `rls-policies.sql`                                                                                 |
| `scripts/check-test-isolation.mjs` (`pnpm test:isolation`) | Tests that contaminate each other                                                                                                           | n/a                                                                                                                                         |

Most of them exist because the failure already happened once. The typecheck
guard was written after finding that many kons were not being checked at all, so
files that did not even parse lived alongside a green `pnpm typecheck`. The
facade guard came after a convenience `import` reopened a cycle two lines below
the comment that forbade it. The loader guard came after a kon with a schema,
service, policies, migration and manifest, compiling and with passing tests,
turned out to be a library the loader could not mount. The `.where()` guard
uncovered the most places: every one had the same shape, an optional filter
added inside an `if`, which is how you write that, and each one returned or
touched too much without raising a single error.

A green that lies costs more than a red.

## Distributing kons

The core (`apps/api`, `@kitsuden/engine`, `@kitsuden/shared` and the
`packages/core/*` batteries: datasets, media, blocks) is what always ships. Kons
are not part of it, and nothing in this repository publishes them to npm: they
come from a kons repository
([`kitsuden-kons`](https://github.com/Kitsuden/kitsuden-kons)) or from a signed
registry, and are installed with `kitsuden kon add`.

- How installing works, `KITSUDEN_KONS`, and kons inside the Docker image:
  [kons/installing.md](kons/installing.md)
- What a kon must carry (`kon.json`, `index.ts`, `migrations/`) and how to
  release one: [kons/publishing.md](kons/publishing.md)
- Signed, versioned kons: [kons/registry.md](kons/registry.md)

The API image installs the kons you list in the `KITSUDEN_KONS` build argument.
Building them all into the image on purpose makes enabling one an update of the
`modules` table from the panel instead of a build and a deployment.
